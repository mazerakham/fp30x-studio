FP-30X Studio, as a desktop app

Two independent design passes, 2026-08-22. Both were derived from the record — 83 Claude Code transcripts on this machine, the fp30x-recording skill, PROJECT_LOG.md, the takes directory and the Linear board — not invented. Committed as 87da9ad and ab1c299.

The brief. A native macOS app with the same features as the Python toolkit, that survives sleep, and that you operate yourself with no LLM in the loop.

The architecture recommendation: SwiftUI shell, the existing C capture as a supervised child process, the existing Python stack as cancellable subprocesses. Rewrite nothing that works. Verified today that SwiftUI/CoreMIDI/AVFAudio build with the Command Line Tools SDK — no Xcode required.

The product finding: every indicator the current tool shows is about the software, not about the take. The connect line, the note feed, the packet counter and the live process have each reported healthy while nothing was being recorded.

Three things the designs turned up that are already true

1. No inactivity timeout can be honest on this piano. The FP-30X sends no Active Sensing over BLE-MIDI — a byte census of tonight's 27-minute take is 0x80, 0x90 and 0xB0 and nothing else — so silence and a dead radio are the same on the wire. The longest genuine silent gap inside that known-good take is 147.6 s, past watch.py's 120 s red threshold. The existing alarm would have fired inside a perfect performance.

2. The green light I wrote this afternoon could lie. It watched file size, and a .fp30 grows by nine comment lines at open and one more on a reconnect — so it flipped GREEN with zero MIDI received. Reproduced and fixed: it counts note-ons now. Verified against tonight's take, 6037.

3. The reconnect fix existed but had never been committed or rebuilt. MIDINotifyProc on kMIDIMsgSetupChanged plus the app holding its own IOPMAssertion — written, sitting dirty in the tree, and make was reporting nothing to do while the built binary predated it. Committed as ab1c299. The venv was also missing soundfile and scipy, which is why ten tests failed and why tonight's gain probe silently returned an empty string. 319 tests pass now.

Product design

FP-30X Studio — product design, v1 (native macOS)

Status: draft for review. Written 2026-08-22 from the transcript record, the fp30x-recording skill, PROJECT_LOG.md, the takes directory, and the Linear board. Companion to the architecture design.

Summary

The job. Jake sits down at a Roland FP-30X, plays for twenty minutes, and wants what he played to exist afterwards — as a file he can listen to, send to a friend, and find again in a month — without any of that costing him attention while he is playing, and without a failure being able to hide from him. Today that loop only closes when an LLM operates twelve command-line modules on his behalf. v1 is that loop, closed by the software.

The three moments.

  1. Arming. He is on the bench, hands ready. He needs one signal, from several feet away, that says go — and it must keep saying go for the whole session, because the ways this fails are silent.
  2. Landing. The piece is over. He needs a listenable, shareable, correctly-named file without answering a single question first.
  3. Return. A week or a month later, he needs to find the right take and know what it is — in particular, to tell a 3:22 fragment from a 23:32 complete performance at a glance.

The single biggest thing the current tool gets wrong.

Every indicator it shows is about the software, not about the take.

connected: FP-30X MIDI Bluetooth, the live note feed, the packet counter, the running process, fp30x-capture -l — each of these has reported healthy while nothing was being recorded, and each lie has a named cost in the skill file: 27 seconds of a nocturne's opening (2026-08-21), six minutes of a nocturne (2026-08-21), eleven minutes (2026-08-20). The one signal that has never lied is the size of the file on disk, and the shipped GUI (fp30x_studio/app.py) does not look at it. It also still uses the 2 ms Python poll loop in core.py that native/fp30x_capture.c replaced on 2026-08-17, writes takes as 2026-08-16 15.03.58.mid, and calls none of the twelve modules built since. It is a day-one demo that the rest of the project grew past.

The same disease reached the output side, and shipped: segment.py and stitch.py read only the first MIDI message of each CoreMIDI packet, silently dropping 5–9% of the notes in every .mid export — 135 of 1,930 on one take (JPA-149, 2026-08-20). A master built through that path was uploaded to Drive before anyone noticed, and has since been replaced. It reported success throughout.

Every rule in this document descends from that one correction: an indicator that is not a function of bytes on disk does not ship, and a stage that can lose data silently must count what went in against what came out.

1. Who this is for and what job it does

  • One user. Jake Mirra: PhD mathematician, working engineer, serious amateur pianist. No onboarding, no tooltips, no first-run tour, no second user to design around.
  • The job: get what he played off the piano and into a keepable file, without taking his attention off the piano, and without ever being able to fail quietly.
  • The constraint that defines it: the capture path is BLE-MIDI, which goes deaf while reporting success. Therefore the product is not a recorder — it is an honest witness to a recorder. That is the whole design.
  • What success looks like: he plays; he never thinks about the software during the piece; afterwards there is a correctly-named file he can play, and a month later he can find it.
  • What it is not: a DAW, a notation editor, a practice tool, a research bench.

The founding request, in his words, is the whole scope statement:

"it seems clear to me that it's time we release a desktop for mac os version of the fpx studio software. Write it in some suitable coding language, give it the same features, and make sure it survives sleep. […] distilling it down to a perfect software solution that suits my needs and doesn't need an LLM to run everything for me." — T-D, 2026-08-22

3. The arming experience

What the light is driven by

Bytes landing on disk. Nothing else. The skill states the rule and names its casualties; greenlight already implements it in 40 lines of bash. v1 inherits the rule verbatim:

"The file size is the only thing that cannot lie. Check that, and nothing else." — S

Concretely: the app stats every armed sink at 4 Hz and holds two numbers per sink — the size at arming, and the wall-clock time of the last observed increase. Every visual state below is a pure function of those numbers plus the link probe (below).

The one hard problem, stated honestly

After green, silence and a dead radio look identical at the MIDI layer. There is no heartbeat to fall back on: the FP-30X sends no Active Sensing (0xFE) over BLE-MIDI. Byte census of 2026-08-22-home.fp30, a 27-minute take: status bytes are 0x80 ×6517, 0x90 ×6037, 0xB0 ×3366 and nothing else; fp30x_capture.c filters no real-time messages, so their absence is the instrument's, not ours. (Measured for this document.)

And a pure timeout cannot save it, because real silence is long. The longest genuine inter-message gap inside that known-good take is 147.6 s — which exceeds watch.py's RED_S = 120 threshold. The current amber/red rule would have raised a false alarm inside a perfect take, which is exactly the failure the skill records for supervisor v3: "works, but cycles during long pauses and litters empty files." A silence timeout is not a link detector and v1 must not ship one as if it were.

So the link needs an out-of-band witness. Two candidates, in preference order:

  1. The room mic. Already produced a file today (2026-08-22-home-room.wav, 140 MB, 27 min). It sits ~25 dB below usable as audio, but it does not need to be audio — it needs to answer one boolean: is a piano sounding right now? If the mic hears playing while no bytes are landing, the link is dead, with certainty. This is the disambiguator, and it is the only one that survives the radio dying. [inference: the RMS-gate design is mine; the mic-as-witness idea is from S.]
  2. A CoreMIDI endpoint probe. kMIDIPropertyOffline on the source endpoint, and/or a MIDINotifyProc on kMIDIMsgSetupChanged — the latter is already named in S as the real fix for the capture's inability to reconnect. [inference: whether Offline actually flips for a BLE-MIDI source that has stopped delivering is unverified and is the single highest-value experiment before implementation. If it flips reliably, the mic becomes optional.]

The states

Five, not three. The extra two exist because collapsing them is what produced the lies.

state condition meaning colour
RED — ARMING ≥1 armed sink has not grown since arm not recording yet red, full-bleed
GREEN — RECORDING every sink grew since arm, and a byte landed < 20 s ago recording green, full-bleed
GREEN — QUIET every sink grew since arm, last byte ≥ 20 s ago, link probe alive, room quiet you stopped playing; still armed green, dimmed 40%
AMBER — DEGRADED ≥1 sink stale while ≥1 other still growing one path lost; the take is safe amber
RED — LOST link probe reports gone, or mic hears playing with no bytes landing not recording; act now red, pulsing

Rules that make the states worth having:

  • RED is the default at arm. Green is earned by a byte, never by a connect line. S: "Never say 'play' on the strength of the connect line. That line is a lie about the radio."
  • RED — ARMING asks for exactly one thing: one key. Not the piece, not a cable, not a setting, not a decision. S: "Never ask him for a second thing."
  • GREEN — QUIET is dim, not amber. Dimming carries "nothing is arriving" without implying fault. Amber for a rest would train him to ignore amber, which is how the 2026-08-20 real drop alarm got dismissed and cost eleven minutes (S).
  • DEGRADED never says stop. Two sinks exist so that one can die without ending the take. The headline stays STILL RECORDING; the fault is the subtitle.
  • RED — LOST states its own evidence. "the room mic heard you playing at 12:59" — because he has been given confident wrong status three times and the only repair is showing the reasoning.

Bench legibility

  • The light is the window, not a dot in it. Full-bleed field, one word, ≥ 96 pt. Readable at 8 feet, in peripheral vision, by colour alone.
  • Colour is never the only channel — the word changes too (DO NOT PLAY / RECORDING / STILL RECORDING / NOT RECORDING). [inference]
  • Silent. No sound, ever, unattended. S: "--no-play matters. He is often at the keyboard and will tell you not to make sound." Also T-C: "I also want an agent searching (without making sounds on this laptop)."
  • Quiet. No log, no counters, no packet stats, no paths in the arming view. Note count and elapsed time live in one small line under the field. T-D: "get it to not talk so god damned much."

What arming actually does, in one press

  1. Take a power assertion (PreventUserIdleSystemSleep + PreventSystemSleep) for the session. S: "SLEEP KILLS THE CAPTURE — pin it off before you say GO." This is also a literal line of the commissioning request: "make sure it survives sleep" (T-D).
  2. Open two independent capture sinks on the one CoreMIDI source, writing two files. Cheap; survives a process or disk fault; does not survive a BLE drop, which is why the mic is the third. S.
  3. Start the room-mic witness.
  4. Register a MIDINotifyProc so a setup change reconnects instead of going deaf.
  5. Show RED. Wait for bytes on every sink. Show GREEN. Say nothing else.

4. The post-session flow

The default path has zero questions

postprocess (written today, ~/.claude/skills/fp30x-recording/bin/postprocess) is the working prototype of this and its header quotes the requirement:

"This should all be an automated pipeline that you can run in the background while continuing to talk to me." — T-D, 08-22

Pressing Stop starts it. Nothing is asked. The sequence, all of it already implemented as Python modules:

stop → ingest (incremental, resumes at a byte offset)
     → segment list
     → pick the longest segment as the performance
     → clip it, chasing CC64 across the entry
     → identify against 122,847 themes
     → for BOTH voices: gain-probe at 0.1, render at the computed gain,
       convolution hall (wet 0.28, RT60 2.1), encode to m4a
     → append the integrity record to takes/PROVENANCE.md
     → the take appears in the library, playable

Two details that are settled and must not become options: the gain probe (probing at 1.0 clips and then reports the clipping point rather than the signal) and never peak-normalise after compressing (it produced a "compressed" file 4.4 dB quieter than its linear control). Both from S, both bought with a bad master.

Both voices render by default. This is the move that removes the questions: electric and acoustic are cheap relative to the capture, so "which voice?" stops being a prompt and becomes a toggle on the finished result. postprocess already does this today.

Where the choices go

The choices he sometimes wants are real. They go after, on the result — never before, as a modal.

choice default where it lives
voice electric (settled: S) A/B toggle above the player; re-renders in background, keeps playhead
dynamics linear (settled: S) second toggle: linear / compressed 3:1 @ −20. Linear is his stated preference; compression exists because "I have maxed out every speaker and the beginning is too quiet" (T-C, 08-21)
space hall (settled: S) third toggle: hall / dry
which segment the longest a segment strip under the waveform; click any segment to re-cut. The full segment list table (start, dur, notes, n/s, stops, range, vel, key) is one disclosure click away — it is genuinely useful and genuinely not for the bench
where it starts first note of the chosen segment drag the left handle; pedal is chased across the new entry automatically

His settled combination — electric / linear / hall — is the default of defaults, and the app should render that one first so it is playable while the acoustic is still encoding. [inference: the ordering.]

The rule the flow exists to enforce

No modal question ever stands between a finished take and a playable file. Every adjustment is applied to something that already plays. Corollary: the app never blocks on render — the take is in the library the moment the clip exists, with the render state shown in the row.

5. The take library

What went wrong, precisely

Two files differing by one word nearly published a 3:22 fragment as a complete nocturne (S, T-C). The root cause is that the durable identity of a take is its filename — the filename is what travels to Drive, to YouTube, to Sarah — while everything that makes a take distinguishable (duration, completeness, piece) lived only in an agent's context.

Naming

Canonical, generated, never hand-typed:

Jake Mirra - <Work> - <COMPLETE|SEGMENT|STITCHED> <M>m<SS>s - <YYYY-MM-DD>.<voice>.<ext>

Jake Mirra - Chopin Nocturne in B major Op. 62 No. 1 - COMPLETE 9m37s - 2026-08-17.electric.m4a
Jake Mirra - Chopin Nocturne in B major Op. 62 No. 1 - SEGMENT 3m22s - 2026-08-21.electric.m4a

Raw captures keep YYYY-MM-DD-<slug>.fp30; clips go to takes/clips/; masters to masters/. The word and the duration are both in the name, in that order, so the two files above sort adjacently and differ visibly in the first field that differs.

Completeness is computed, not typed

The skill's rule — "Put FULL, COMPLETE or SEGMENT in the name" — is a human protocol patching a missing feature. The data already knows, and the pipeline already extracts every term needed. From P:

badge derived from
COMPLETE stream ended cleanly (trailer present), no notes held at end beyond the final pedalled chord, no orphan note-offs at the head
JOINED LATE the take opens with orphan note-offs — the structural signature of a stream joined mid-note (four of them, 2026-08-21)
CUT held_at_end > 0, or the trailer is missing — the capture stopped while he was playing
STITCHED assembled by stitch.py from ≥2 takes; carries the seam offset and its vote margin
FRAGMENT a segment clipped out of a longer take, not the whole of anything
POLL-LOOP captured before 2026-08-17 through the 2 ms Python poll loop. 161 of 799 gaps read exactly 0.000 ms and nothing at all falls between 0 and 2.083 ms in 804 events — rolled chords and grace notes were collapsed at capture time and are unrecoverable (JPA-129). Five such takes are in the directory today. Timing questions about them are meaningless and the badge says so

A badge the machine cannot justify is not shown.

Two preservation rules

A .fp30 is irreplaceable; everything else is cache. JPA-158 states it plainly: "You cannot re-play a take." Renders, clips, indices and masters are all reconstructible from the capture and a command. So: the app never deletes, moves, or overwrites a .fp30; a "delete" on a take deletes its renders and offers the capture separately, with a different confirmation. The .index/ SQLite files are explicitly derived and deletable.

A render is verified against its source before it is offered. The note-drop defect described in the summary was invisible because nothing compared the exported .mid to the take it came from. Every render records the note count going in and the note count coming out, and a mismatch is a red row, not a log line.

The sparkline is note density over the take. It does two jobs at once: it makes a 23-minute session visibly different in shape from a 3-minute fragment, and it makes the multi-piece structure of a long session legible before any click — that is the "I was playing some random stuff. Then did a take of rachmaninoff. Then practiced… Then at a certain point I started doing interesting stuff in C-major. Find that point and clip it for me" problem (T-C, 08-20), answered by looking rather than by asking. [inference: the sparkline; the underlying segment data is real and already computed.]

link GOOD is the take's own integrity verdict, already generated per-take into PROVENANCE.md — pairing completeness, inferred loss, 5 ms lattice conformance. It answers "was this take any good" before he spends nine minutes listening to find out.

One thing the library must not claim

.fp30 records the key pressed, not the pitch that sounded. Transpose and Master Tuning never reach the MIDI stream — verified by experiment on 2026-08-20, four repetitions of one phrase at different settings producing byte-identical note numbers (S, JPA-155). So a render can be in a different key from what he heard in the room, and the app cannot detect it. The detected-key field is therefore labelled key as played on the keys, and when a key reading disagrees with him the app defers: he plays scales like G A B♭ C♯ D E♭ F♯ G, and the likelier fault is a detector collapsing a non-traditional scale onto the nearest diatonic set. [inference: the label wording.]

Live, never cached

The library is a live view of ~/Music/FP-30X Studio/takes/ via FSEvents. There is no refresh button because there is nothing to refresh. Direct response to "it doesn't have any of my recordings / isn't autorefreshing / has no refresh button" (T-B, 08-18).

6. The identifier, presented honestly

What it actually is, and what it is for

fp30x_studio/identify/ matches melodic interval n-grams from the live note stream against a 122,847-theme corpus, using Shazam's alignment-histogram trick with score position in place of time. No model is called anywhere in it. It is genuinely good work and it is genuinely thin evidence, and the design problem is showing both at once.

The framing that makes the design tractable is from the project's own product thesis (JPA-147):

"At a MIDI piano the user is the source and knows what he played. The demand is not identification, it is labelling without effort."

He is never asking the app what is this. He knows. He is asking it to write down what he knows, so that a year of takes carries its own index. That reframe decides every choice below: the identifier's job is to make a correct label cheap to accept, not to be right.

The five facts that must shape the presentation

1. Today's verdict was 0.4% coverage. From T-D, 2026-08-22:

"23:32, 6751 notes. The identifier says Chopin, Polonaise-Fantaisie in A♭, Op. 61 — twice, conf 0.95 and 0.97, but only on ~30-note windows out of 6751, so treat it as a guess until you tell me otherwise."

Two 30-note windows out of 6,751 notes is 0.4% of the performance. A confidence number without a coverage number is a lie by omission, and 0.95 is exactly the kind of number that gets glanced at from a piano stool and believed.

2. The high-confidence numbers in the historical record were self-recall. From L and JPA-149: four segments of 2026-08-17-session.fp30 returned 0.949, 0.997, 0.993 and 0.999 — against corpus themes derived from that same take, and unchanged when the corpus doubled underneath them, which is what a tautology does. docs/label-segments.html already flags these with a circular badge. v1 inherits that badge as a first-class state.

3. When it cannot align a performance, it does not refuse — it reaches. This is the most important fact in the section and it was itself discovered by correcting a wrong correction (JPA-149, 2026-08-22):

"My earlier comment said the Chopin segment 'produces no verdict at all'. That is wrong, and the softer version is the more flattering one."

The Op. 62 segment does answer. It answers Anonymous, "HOERT DIE LERCHE SIE SINGT", Op. 150, on 6 aligned hits at margin 0.333 — while the corpus holds 85 indexed theme windows of the actual work from the Chopin Institute's scores. Why the right answer lost:

performance   E  F# C# B  A# G# F# D#     intervals   2, 7, -2, -1, -2, -2, -3
score         E     C# B  A# G# F# D#     intervals     -3, -2, -1, -2, -2, ...

Same theme. One interpolated F#. The matcher votes on 3-grams, so one inserted note reframes everything downstream: 5 of 13 interval 3-grams survive, the true match falls under the gate, and something else clears it. JPA-149's own conclusion:

"A false positive is a worse failure than a refusal, because a refusal is visible and a wrong answer is not."

The test suite had a hole shaped exactly like this: test_removing_the_answer_from_the_corpus_ produces_silence_not_a_guess passes, but it only covers a piece absent from the corpus — not one present that fails to align. Different failure modes; one was tested.

4. His verdicts are already collected, and they say the confidence number is not usable as a UI primitive. takes/labels.json holds 27 verdicts — 17 confirm, 5 correct, 4 reject, 1 unknown — as of 2026-08-20. Read against the confidence the matcher assigned:

Five confirms at conf ≥ 0.99 are genuinely right. But a 0.865 was wrong and three 0.000s were right. Any surface that gates on this number will suppress correct answers and announce wrong ones — in both directions, on his own labelled data. Two consequences for v1:

  • Sub-threshold proposals are shown anyway, marked as such. JPA-148 predicted the case exactly: "a 0.466 that he confirms is a threshold that is too high, and there is no way to know which without asking him." It then happened.
  • A verdict is never presented as a probability. It is presented as evidence he can check, and the number that actually discriminates — coverage — is stated in the same breath.

5. One segment can contain more than one work. His own correction, in labels.json: "Multiple pieces, including Rondo A La Turca starting toward the middle. Not a clean label." The label schema must admit a list, and the correction field must accept free text. A UI that forces one work per segment will collect wrong ground truth.

How a verdict is shown

Never a bare confidence. Three numbers or none, phrased as a falsifiable sentence:

┌───────────────────────────────────────────────────────────────────────────┐
│  PROBABLY   Chopin — Polonaise-Fantaisie in A♭, Op. 61                    │
│                                                                            │
│  matched 30 of 6,751 notes (0.4%) in 2 places                             │
│  clear of the runner-up (Chopin, Op. 44) by 4 aligned intervals           │
│  ▏▏                                                          coverage 0.4% │
│                                                                            │
│  [ ✓ that's right ]   [ ✗ no — it's … ]   [ skip ]                        │
└───────────────────────────────────────────────────────────────────────────┘

Three registers of language, keyed on coverage and separation rather than on the confidence product alone:

  • IS — ≥10% of the take's notes matched, across ≥3 separated windows. "This is Chopin, Op. 62 No. 1." [inference: the thresholds are proposed, not measured — they need calibrating against labels.json.]
  • PROBABLY — fires but thin, as today. Coverage stated in the same breath, always.
  • NOT IDENTIFIED — shown when nothing clears the gate, with the caveat attached rather than buried: "Not identified. That is not evidence it is unfamiliar music — a single added chord tone can reframe every n-gram in a passage and cost the true match its hits."
  • CIRCULAR — the matched theme was derived from this take. Shown in place of a verdict, never alongside a confidence. Detection is mechanical: the take's stem appears in Theme.source. Four segments of 2026-08-17-session.fp30 match at 0.949–0.999 and hold that value when the corpus doubles underneath them, "which is what a tautology does" (JPA-151).
  • OFF BY DEFAULT: nothing — there is no fifth state where the app quietly picks the runner-up. When he corrected the circular ones the runner-up was right twice (Joplin, Fig Leaf Rag; Joplin, Sugar Cane) and wrong once (a nocturne where the answer was Chopin's Ballade 3). Two out of three is not a feature.

His verdict is ground truth

He asked for the correction surface himself, in one sentence:

"Op 55 No 1 was most definitely played yesterday, I could confirm any of these if you just put an html doc up that had recording snippets and then asked me to confirm the labels." — T-B, 08-19

And he has corrected it with more precision than a confidence score can carry:

"Absolutely, that playthrough that you're referring to with the GGFEDCBCDG is STRENUOUS LIFE by SCOTT JOPLIN. You should have paid more attention to the syncopation, preferring [3/16, 1/16] over [1/8, 1/8] for a 1/4-measure. Should give rag." — T-B, 08-18 "The more recently-played piece was Chopin, but you need to get the opus and number." — T-B, 08-18

Design consequences:

  1. Four verdicts, not two, on every take row and in the post-session view — the set JPA-151 settled on and the set his 27 answers actually used: confirm, reject, correct it (free text), don't know. Two-button designs force a reject where the truth is a correction, and the corrections are the valuable half. The store already exists: takes/labels.json, keyed take.fp30#segment, holding verdict, correction, revised_from, and the proposal with its source.
  2. Written on every press, never on a submit, and loaded on start so the queue resumes. Revisions record what they were revised from — he revised one verdict from confirm to reject after listening again, and that reversal is data.
  3. Once he has answered, the machine's guess is demoted to a footnote and never shown as the headline again. A corrected label is the take's name. JPA-151's phrasing of the layout rule: the guess sits in an "identifier said" row underneath, "so the confidence figure is never read as belonging to his label."
  4. A correction is training data, not just a label. Every mismatch between his verdict and the matcher is a case for the corpus and the prefilters — the Op. 62 interpolated-F# defect was found exactly this way. The library needs a view of "takes where he and the matcher disagree", which is the highest-value list in the app for anyone improving it. [inference]
  5. Play the snippet inline. He confirms by ear, not by reading a note list. The existing labelling page synthesises segments in-browser with the pedal chased; a native app can play the actual render.

2.2 The four candidates, costed

Swift + SwiftUI + CoreMIDI + AVAudioEngine. Buys: zero-bridge access to every macOS API in the table — CoreMIDI, IOKit, NSWorkspace, AVFoundation, CoreBluetooth. A real app bundle, a real menu bar, a real Dock icon, real notifications. Structured concurrency (actor, AsyncStream) maps cleanly onto "one supervisor, N writers, a job queue". Verified buildable here without Xcode (§0). Costs: Swift is a poor fit for the CoreMIDI read callback — ARC retain/release and exclusivity checks are not documented as allocation-free, and the callback rule (no malloc, no locks, no syscalls) is real-time-audio practice the current C file already honours deliberately (fp30x_capture.c header comment, and it is honest that Apple's headers contain no verbatim prohibition). Swift also cannot host numpy. So this is not "rewrite in Swift"; it is "Swift shell around two existing runtimes", and the seams between them are the design work. Second cost, stated plainly: nobody in the loop has shipped a signed, notarised macOS app in this project. Without Xcode there is no xcodebuild archive; the bundle, Info.plist, entitlements and codesign invocation have to be assembled by hand in a Makefile. That is a day, not a week, and it is a day nobody has spent. GUESS: I believe an ad-hoc-signed local bundle needs no notarisation for Jake's own machine; I did not test whether Gatekeeper's quarantine attribute interferes when the bundle is built locally rather than downloaded. It should not — quarantine is set by the downloader, not the compiler.

Rust + a GUI toolkit (egui / Tauri / gtk-rs). Buys: a good real-time story — no_std-style discipline in the callback is natural, and coremidi/core-foundation crates exist. Costs: Rust is not installed on this machine (rustc: command not found), so it starts with a toolchain install. Every Cocoa API in the table reaches Rust through objc2/cocoa bindings that are third-party, version-skewed, and — for NSWorkspace sleep notifications and IOPMAssertion — thin enough that you write the extern "C" declarations yourself. You end up maintaining a private Cocoa binding layer for a single-user app. egui gives you an immediate-mode canvas, not a macOS app; Tauri gives you a webview, which is Electron's cost with Rust's build times. Rejected: it buys real-time rigour in the one place that is already 538 lines of proven C, and pays for it everywhere else.

Electron. Buys: the fastest path to a good-looking UI, and this project already produces excellent self-contained HTML (docs/timbre-workbench.html, 167 KB). Node 26.7.0 is installed. Costs: three fatal ones. (a) Memory. The machine has 8 GB. The identifier alone is 497 MB resident (§11). A modern Electron shell is 300–600 MB before you draw anything. (b) No CoreMIDI, no IOKit, no NSWorkspace without a native addon — so you write the C anyway, plus an N-API binding, plus the JS on the other side; three languages to hold one assertion. (c) The timer problem is already documented in this project. JPA-139 records the timbre workbench's setInterval throttling to ~1 s when the tab was hidden, past the 0.25 s lookahead, causing ~7 dropped voices/second until the lookahead was made adaptive. A liveness light whose clock stops when the window is backgrounded is the exact failure this application exists to prevent. Rejected.

Keep Python; wrap it in a native shell (py2app / PyInstaller / a thin Swift launcher). Buys: zero rewrite. Everything works on day one. Costs: the shell still cannot own the assertion or the sleep notifications without a native component, so you are back to a Swift or ObjC layer — at which point the question is only how much of the app lives above the line. And the existing Python GUI is direct evidence against Tk: fp30x_studio/app.py had to rebuild every button out of tk.Label because macOS Tk silently ignores -background on tk.Button, and shipped with two buttons both reading "Stop" because start_record() never reset the Play label (transcript b8a2bca6, 20:09, Jake's first UI defect report: "the button font is bad as you get a light-grey-on-white when I'm playing. Three rules define the line:

  1. Anything whose lifetime must equal "armed" lives in Swift, in the app process. The power assertion, the sleep observers, the liveness state.   2. Rewriting it in Swift buys nothing and risks a retain on the audio thread.
  3. Anything that is arithmetic over a finished file stays in Python. It is not on a deadline, it is tested, and it is where all the measurements live.

The consequence is that fp30x-capture stays a separate process, not a Swift class. That is deliberate: it means force-quitting the UI, or the UI crashing, does not stop a take. The property that has actually saved recordings in this project is that the capture is a small boring process appending to a file that can be stat-ed by anything. Keep it.

4. The capture engine

4.1 What is already correct

native/fp30x_capture.c as it stands today (uncommitted, §1.1):

  • MIDIInputPortCreateWithBlock on the soft-deprecated MIDIPacketList API on purpose — MIDI 1.0 bytes with no UMP repacking between the driver and the file. Both APIs carry the same MIDITimeStamp, so nothing is given up on timing (JPA-129).
  • Callback does exactly: read timeStamp (substituting mach_absolute_time() and counting ts_zero when it is 0, which is documented to mean "now"), memcpy ≤256 B into a preallocated slot of a 16,384-slot SPSC ring, bump an atomic. No malloc, no lock, no syscall.
  • Writer thread drains, formats <abs_ns> <HEX …>, write()s, fsyncs every 0.25 s.
  • midi_notify on kMIDIMsgSetupChanged → connect_sources() (idempotent; reconnecting an already-connected source is harmless) → writes # setup_changed reconnected N and fsyncs.
  • hold_awake() / release_awake() around the whole capture.

That is the right design. Keep it. The remaining work is in what the app does around it.

4.2 Reconnect policy — what is missing

Three gaps in the current midi_notify:

  1. It reconnects, but does not record what it lost. The marker says how many sources were reconnected, not when delivery stopped. The take file has no way to express "music happened here and we did not receive it". Fix: on kMIDIMsgSetupChanged, write two lines — # link_lost <unix_ns> <last_packet_ns> when the matching source count drops to zero, and # link_restored <unix_ns> reconnected <n> when it comes back. The pair delimits a gap of known wall-clock extent.
  2. It fires on every setup change, including irrelevant ones. Plugging in a USB audio interface fires kMIDIMsgSetupChanged too. Reconnecting is idempotent so this is harmless, but the marker is noise, and — critically — a comment line is bytes on disk, which is what the green light counts (§6.5). Fix: only write a marker when the set of connected matching endpoints actually changed. Track MIDIObjectRef + kMIDIPropertyUniqueID of connected sources and diff.
  3. No backoff, no ceiling. If the radio flaps, connect_sources() runs on every notification. Fix: coalesce notifications on a 250 ms timer, and after 10 failed reconnects in 60 s escalate to the app (which is the thing that can tell Jake). A capture process must never restart itself — supervisor v1/v2/v3 all failed (SKILL.md), and v3 in particular littered empty takes. Restart policy belongs in the app, keyed on bytes, and it must reuse the same output file (the format is append-only, so a restart appends a fresh header block into the same take — which is why the reader must treat headers as a sequence, §8.2).

4.3 What the app does with the gap

The app owns the interpretation. On seeing # link_lost:

  • Transition the light to DEGRADED immediately (§6).
  • Record a Gap(startNs, endNs, cause: .setupChanged) in the index.
  • On # link_restored, do not go back to GREEN. Go to armedNotReceiving, because the BLE link starts delivering somewhere between 0 and 40 seconds after CoreMIDI reports the source connected — on 2026-08-21 the file was created at 18:14:04 and the first byte landed at 18:14:31, twenty-seven seconds of playing recorded nowhere, and the take opened with four orphan note-offs (SKILL.md; this is also why stitch.py exists). Only a real packet returns the light to GREEN.
  • Leave the gap in the take. Do not stitch automatically. stitch.py already does a defensible splice — 4-grams of pitch from the body's opening voting for an alignment offset in the head, and refusing when no offset dominates — but that is an edit, and edits are Jake's call, made knowingly, on a named artifact (§8.4). It works: on the two half-nocturnes of 2026-08-21 the votes produced a clean peak at 45.1 s, corroborated structurally because the body's four orphan note-offs are E5/G♯4/E4/C♯4 — exactly the pitches of the head's chord at 45.08–45.12 s. The takes overlap to the resolution of a single chord, and his verdict was "The seam came back indetectable. We got it." Two refinements are in the code and must survive the port: anchor the body on its first note-on, not its first raw message (which is an orphan note-off 0.510 s earlier and became dead air), and cut the head late enough that its chord still rings so the body's own orphan note-offs release it.

Byte-growth events come from DispatchSource.makeFileSystemObjectSource(fileDescriptor:eventMask: [.write, .extend], queue:) on each take file — event-driven, no polling — with a 1 s watchdog timer as a backstop in case kqueue coalesces an event away. That distinction is the whole green light.

5.2 The app takes both assertions, and refuses to arm without them

PowerGuard.arm() calls IOPMAssertionCreateWithName twice — PreventUserIdleSystemSleep (the take) and PreventUserIdleDisplaySleep (so the green light stays on the screen he is glancing at). Both are released in disarm(), and in a deinit, and by an atexit handler.

Should the app refuse to arm without an assertion? Yes — refuse. The argument: the green light's whole meaning is "your playing is being recorded". On a machine that can idle-sleep, that claim has a 30-minute fuse on it and no way to tell the player. The failure mode of IOPMAssertionCreateWithName on a healthy Mac is essentially never, so the refusal costs nothing in practice and removes an entire class of silent loss.

The escape hatch is explicit and self-documenting: a Preferences toggle "Allow the machine to sleep while recording", off by default, which when on writes # sleep_allowed 1 into every take header. If a take turns up short and the header says that, the reason is in the file.

The capture children keep their own assertions too (hold_awake() in fp30x_capture.c). Duplicate assertions are free and the redundancy is the point: neither the app nor a child can be the single process whose exit un-pins the machine.

5.3 Sleep and wake notifications

let nc = NSWorkspace.shared.notificationCenter
nc.addObserver(forName: NSWorkspace.willSleepNotification,      …)  // system is going down
nc.addObserver(forName: NSWorkspace.didWakeNotification,        …)
nc.addObserver(forName: NSWorkspace.screensDidSleepNotification,…)  // display only — informational
nc.addObserver(forName: NSWorkspace.screensDidWakeNotification, …)

willSleepNotification is delivered synchronously and macOS waits (briefly) for observers to return, so the handler must be short and must not await. It does exactly three things:

  1. Write # host_sleep <unix_ns> into every open take, via a pre-opened fd and a preformatted buffer, then fsync. (The capture children each fsync every 0.25 s independently; this marker is the app's, and it goes in through the same append-only fd so the ordering is the kernel's.)
  2. Snapshot the last packet ns per take, in memory.
  3. Set the liveness state to sleeping.

didWakeNotification writes # host_wake <unix_ns>, transitions to armedNotReceiving, and starts a 60-second reconnect window. Display sleep is not a capture event — MIDI keeps arriving with the screen off. It only matters because the green light is invisible, which is why the display assertion is taken.

5.4 What a wake does to the take

The take is one file. It is not split, and the pieces are not silently joined.

Between # host_sleep and the first packet after # host_wake there is a gap of known wall-clock extent and unknown musical content. That becomes a row:

CREATE TABLE gap (
    id          INTEGER PRIMARY KEY,
    start_ns    INTEGER NOT NULL,   -- mach ns of last packet before
    end_ns      INTEGER NOT NULL,   -- mach ns of first packet after
    wall_start  INTEGER,            -- unix ns from the marker, when present
    wall_end    INTEGER,
    cause       TEXT NOT NULL,      -- host_sleep | setup_changed | capture_restart | unknown
    keys_down   TEXT NOT NULL       -- JSON: pairer state at start_ns
);

Consequences that must be enforced, not documented:

  • segment list treats a gap as a hard boundary, whatever its duration. A 40 s musical silence and a 40 s hole look identical in the packet stream and are not the same thing.
  • Notes held across a gap are closed at start_ns with closure='gap'. The existing pairing layer already records which observation closed each interval and only counts closure='note_off' as a measured release (JPA-136); gap slots straight into that vocabulary and inherits the honesty.
  • Any clip, render or master whose span intersects a gap carries GAP in its filename and a line in PROVENANCE.md. This is the same rule that produced FULL / COMPLETE / SEGMENT after a 3:22 fragment was nearly published as a complete nocturne.
  • A take containing a gap can never be labelled COMPLETE by the automatic namer in postprocess.

(b) MIDI Device Inquiry SysEx round-trip. Send F0 7E 7F 06 01 F7 to the FP-30X MIDI Bluetooth destination and look for an Identity Reply (F0 7E … 06 02 …) on the source within, say, 2 s. Roland instruments generally answer this. Risk: GUESS — the FP-30X manual's MIDI implementation was not checked for Device Inquiry support, and no take on disk contains an F0 byte to confirm it round-trips.

What to do about not knowing: run the one-hour experiment before Milestone 2 — pair the piano, try (a), try (b), record the result in PROJECT_LOG.md. If both fail, the Probing state collapses into "GREEN, quiet for N minutes" with the minutes shown, and the app cannot distinguish a rest from a dead radio — which is exactly the situation today, so nothing is lost, but the design should say so out loud rather than assume the probe works.

7. Redundancy

7.1 Two writers on one radio — what it is worth, measured

Two fp30x-capture processes on the same CoreMIDI source, run today at 21:00:28 and 21:00:29 UTC:

408344 2026-08-22-home.fp30          15930 lines
408344 2026-08-22-home-mirror.fp30   15930 lines
packet lines md5, both: dc3ec22b3dea0e157c98dc4fec1468bc
first packet, both:     183827810000000 B0 40 16

Byte-identical bodies, identical mach timestamps. This is worth stating precisely because it cuts both ways:

  • What it buys: survival of a process crash, a writer thread wedging, an fd going bad, a disk hiccup on one file. Cheap — one more process, 400 KB, no measurable CPU.
  • What it does not buy: anything about the radio. Both are downstream of one CoreMIDI client set and one BLE link. A drop is invisibly identical in both files. It also buys no independent information for reconciliation — the mirror can never fill a hole in the primary, because it has the same hole.

So mirroring is a cheap fault-tolerance measure and not a redundancy measure in the sense that matters. Arm it by default (Preferences → Mirror writers: 1), and never let the UI imply that two green paths mean the radio is safe.

Design consequence: the liveness monitor requires bytes on every armed file for GREEN, and raises Degraded(path:) when one writer stalls while another grows — because that divergence is precisely the fault the mirror exists to catch, and it is the only fault it can catch.

7.2 A genuinely independent MIDI path

~/workspace/audio/bt_midi.py is a userland BLE-MIDI GATT client (bleak/CoreBluetooth) that bypasses CoreMIDI entirely. It is not a redundant path in practice: a BLE peripheral accepts one central connection, and macOS's CoreMIDI BLE driver holds it. The README says as much — it is useful "when the piano is unpaired and still advertising". Treat it as a diagnostic, not a writer.

The only genuinely independent MIDI path is USB (§7.4).

When it was last on the bus (2026-08-20) macOS enumerated it as Roland Digital Piano (VID 0x0582, PID 0x029c) and left it !registered, !matched with zero interfaces — no CoreMIDI port, no CoreAudio device. What the app does about it now, before the cable arrives:

  • Model the capture path as a first-class field, selected by endpoint name and recorded in the header — # path ble | usb | virtual — and display it on the take row.   • When a Roland Digital Piano CoreMIDI source appears, the supervisor offers it as an additional armed path, not a replacement. When a matching CoreAudio device appears, the witness switches from the mic to it and stops being a witness — it becomes the instrument's own voice, which is the thing JPA-155 has been urgent about since 2026-08-19.
  • The USB path also settles the open timing question: whether the 5.000 ms lattice (15,897/15,920 packets today) is the piano's 200 Hz key scan or BLE batching. If USB still shows 5 ms, sub-5 ms timing does not exist on this instrument by any route and every timing question can be closed (JPA-133).

8.2 .fp30 format changes

The format stays text, line-oriented, append-only, greppable. That is the right decision and it is argued in the C header comment: MIDI's worst-case data rate is a few KB/s, so the encoding costs nothing and buys tail, grep, diff and human readability. It is also why a torn write costs at most one line.

Three changes:

  1. Comments become an ordered event list, not a dictionary. rawcapture._consume folds every # key rest line into out.header[key] = rest, so the last one wins — a take with three # setup_changed lines reports one, and a restarted capture's second # started_utc silently overwrites the first. Today's reconnect logging is therefore invisible to every consumer. New shape: 
    @dataclass
class RawEvent:
    byte_offset: int
    kind: str          # started | source | sources_connected | setup_changed
                       # | link_lost | link_restored | host_sleep | host_wake
                       # | sleep_allowed | path | clip_entry_cc | end
    fields: dict[str, str]
    Scan.events: list[RawEvent], with Scan.header kept as a compatibility view over the first occurrence of each key. Existing files parse unchanged.
  2. New markers, all optional and all ignorable by an old reader: # path <ble|usb|virtual>, # link_lost <unix_ns> <last_packet_ns>, # link_restored <unix_ns> reconnected <n>, # host_sleep <unix_ns>, # host_wake <unix_ns>, # sleep_allowed 1.
  3. Extension: accept both .fp30 and .fp30x. The README and rawcapture.py docstrings say .fp30x; every file on disk is .fp30. Reader accepts both; writer emits .fp30; docs get corrected.

8.3 Index schema: bump 1 → 2

SCHEMA_VERSION = 1 in pipeline/store.py. Version 2 adds the gap table (§5.4), a path column on take, and a closure='gap' value. Because the index is derived, migration is deletion: bump the constant, and TakeStore re-ingests when it sees an older version. Measured cost of a full re-ingest of the largest take on disk: 0.29 s. There is no migration problem here, only the discipline of never writing anything to .index/ that is not recomputable.

The checkpoint design stays exactly as it is and should be treated as settled: byte offset + file_size + head_sha256 + pairer state, with a shrink-or-rewrite forcing a full re-ingest. It was verified by replaying a real 353 s take as 17 uneven appends that cut lines mid-record and getting a row-for-row identical index (JPA-136).

9. The processing pipeline as an object

Jake's own framing, 2026-08-22, quoted in bin/postprocess: "This should all be an automated pipeline that you can run in the background while continuing to talk to me." The shell script is the prototype. The app makes it an object.

9.1 One parser, structurally enforced

Before anything else: delete the duplicate .fp30 parsers. segment.py (three sites) and stitch.py each open the file and split lines themselves. That duplication is not incidental — it is why the first-message-only bug came back in the export path after being fixed in the analysis path, and it cost 135 of 1,930 notes on a master that had already been uploaded (JPA-149).

Enforcement, not documentation:

  • rawcapture.scan() is the only function permitted to read a .fp30 byte. Everything else takes a Scan or a TakeStore.
  • A test greps the package for open( on a .fp30 path outside rawcapture.py and fails. The identify package already has a test of exactly this shape — it greps the identification path for model and socket imports — so the pattern is established in-tree and known to work.
  • The Swift side never parses .fp30 for content. It counts packet lines for liveness (§4.4) using a 20-line reader whose only job is "is this line a comment"; it never decodes a MIDI byte.

9.3 The object

protocol Stage: Sendable {
    var id: StageID { get }
    var inputs: [URL] { get }
    var outputs: [URL] { get }
    /// SHA-256 over: input digests + serialised parameters + tool versions.
    func fingerprint() throws -> String
    func run(_ ctx: JobContext) async throws          // must honour ctx.cancellation
}

actor JobRunner {
    func enqueue(_ pipeline: Pipeline) -> JobID
    func cancel(_ id: JobID) async                    // SIGTERM child, delete *.part
    func progress(_ id: JobID) -> AsyncStream<StageProgress>
}

Four properties, each of which is a rule that has been broken:

  • Never blocks the UI. Every stage is a Process on a background queue. Nothing calls waitUntilExit() on the main actor.
  • Never plays sound unasked. Every invocation of segment clip passes --no-play (the default plays the result, and "he is often at the keyboard and will tell you not to make sound"). The app owns playback and starts it only from an explicit user action. This is enforced at the Stage layer, not left to each call site.
  • Resumable. A stage whose outputs exist and whose fingerprint() matches the recorded one is skipped. Fingerprints go in takes/.index/jobs.sqlite3 — derived, deletable.
  • Cancellable and atomic. Every output is written to <name>.part and rename(2)d on success — the trick core.ensure_soundfont already uses for the 38 MB download. Cancellation SIGTERMs the child and unlinks the .part. A cancelled job never leaves a half-file that a later run mistakes for a completed output.

9.4 The pedal chase is part of the clip, not an option

segment clip reads all controller state before the window and writes it into the slice's trailer as clip_entry_cc lines, then injects it at the head of the .mid. CC64 is held across bar lines for tens of seconds — on the open take the pedal is down for 94% of the take across 101 spans — so a clip cut mid-phrase without the chase renders dry. This is Chase Events in DAW terms and it is not a checkbox. The Stage for clip has no parameter to turn it off.

9.5 Where postprocess's heuristics need to become choices

The shell script picks the performance as the longest segment, by an awk over the segment list output. That is a reasonable default and a bad contract — it is a text-scrape of a human-readable table, and it silently picks something. In the app, segment list returns structured segments, the longest is preselected, and the take view shows all of them so the choice is visible and one click from being changed. Same default, no silence.

Likewise the automatic name <take>-COMPLETE-<m>m<s>s: the app must not write COMPLETE when the chosen segment is not the whole take, or when the take contains a gap (§5.4). The naming rule exists because a 3:22 fragment was nearly published as a complete nocturne, two files differing by one word.

10.1 Two engines, one protocol

protocol Renderer {
    var id: String { get }            // "fluidsynth.acoustic", "model.electric", …
    func render(midi: URL, to out: URL, sampleRate: Int) async throws -> RenderReport
}

FluidSynthRenderer — subprocess, FluidSynth 2.6.0, two soundfonts: - acoustic: ~/Music/FP-30X Studio/MuseScore_General.sf3 (38 MB, MIT, auto-downloaded on first run) - electric: ~/Music/FP-30X Studio/soundfonts/jRhodes3/jRhodes3c-stereo.sf2 — a 1977 Rhodes Mark I, five velocity layers. Jake's stated preference is electric / linear gain / hall.

ModelRenderer — python -m fp30x_studio.synth render -p {acoustic,electric}. Not a sampler: every sample is computed from a written-down physical model (inharmonic stiff string $f_n = n f_0 \sqrt{1 + Bn^2}$ with per-partial decay; a tine/FM voice for the Rhodes). 15 of its coefficients are fitted to 38 recorded notes of a 2001 Steinway B (University of Iowa); 7 remain guesses and are labelled as such in the preset, the report JSON, and the page (JPA-154). The UI must carry that label — a preset with 7 guessed coefficients is not the same claim as a sampled instrument, and renders/PROVENANCE.md already states plainly that "nobody in the loop that produced these files can hear."

They coexist as peers in a Voice picker: Acoustic (soundfont), Electric (soundfont), Acoustic (model, 15/22 fitted), Electric (model, unfitted). Same output contract, same post chain, different Renderer.

The acceptance bar for the model renderer is his ear, and it has failed twice. "The ones you showed me earlier were a bit grating… Felt kind of metallic. Scraping my spine. You would have to be human to get it." (50ec5096, 2026-08-18 19:25.) "The sound is extremely 8-bit, does not sound anything like a cool electric piano or grand." This is also why the pipeline must render both voices unattended, as postprocess already does: the only way to settle it is to hand him an A/B.

The related defect, and it is not a timbre issue: "sounds amazing but has no pedal so not very legato" and "Needs pedal though … sounds horrible without it" (885ff9f8, 2026-08-20). 10.2 Gain — the settled facts, as code

// 1. Probe LOW. Probing at 1.0 clips on the electric piano, and a clipped probe
//    reports the clipping point rather than the signal, so the correction is
//    wrong in an unknown direction.
let probePeak = try await fluidsynth(gain: 0.1, midi: midi, to: tmp).peak()
guard probePeak > 1e-6 else { throw RenderError.probeProducedSilence }  // §12, incident 5
let gain = min(10.0, 0.1 * (0.89 / probePeak))
// 2. Take the headroom in the RENDER. fluidsynth's default gain is 0.2, which
//    leaves ~24 dB unused; the first render of the 2026-08-17 nocturne peaked at
//    −24.5 dBFS for exactly this reason. Amplifying a finished 16-bit file
//    instead lifts the quantisation noise with the music.
try await fluidsynth(gain: gain, midi: midi, to: out)

The probe is not a formality: on the same MIDI file, the electric soundfont needed gain 0.34 and the acoustic needed 2.12 — a factor of six between two timbres, which is the five velocity layers of the Rhodes doing real work. A single hardcoded gain is wrong for one of them by 16 dB. (885ff9f8, 2026-08-21; the same session shipped a clipped electric render at −0.0 dBFS whose "linear" file was louder than its compressed one, because the probe had been run at unity.)

And the post chain:

  • Linear (his preference): render → reverb --wet 0.28 --rt60 2.1 → AAC 256k.
  • Compressed: render → loudness --ratio 3 --pivot -20 → reverb → AAC. The mapping is $\mathrm{out}(t) = P + (1-\alpha)(E(t) - P)$ with $\alpha = 1 - 1/\text{ratio}$, monotone in $E$ for $\alpha < 1$, so louder passages stay louder — it compresses dynamics without reordering them.
  • Never peak-normalise after compressing. One boosted transient sets the peak and drags the whole file back down; it produced a "compressed" file 4.4 dB quieter than its linear control (the incident is in loudness.py:168). Makeup gain to a target RMS, then limit. The app has no "normalise" button downstream of the compressor.

10.3 Two integration defects to fix while porting

  1. loudness.read_wav demands 16-bit PCM (if w.getsampwidth() != 2: raise SystemExit). The model renderer writes PCM_24, and postprocess renders at 48 kHz where fluidsynth writes 16-bit. So the two halves of the render stack cannot currently be composed: you cannot compress a model render. Fix: read via soundfile and carry float64 through the chain, writing the bit depth only at the encode stage.
  2. The gain probe failed silently on the one run that mattered. On 2026-08-22 the probe returned nothing because soundfile is not installed in fp30x-studio/.venv, and fluidsynth rendered at its default 0.2 — ~24 dB down. The renders came out acceptable by luck. In the app this is a hard error: a probe that does not produce a number fails the stage (RenderError .probeProducedSilence, above). See §12.

11. The identifier

11.1 What it is

fp30x_studio/identify/ — Shazam's trick moved out of time and into score position. Onsets within 55 ms are one struck event (a chord arrives as a ~5 ms arpeggio); ornament runs collapse to their principal note (one Chopin take carried 38 trill runs); three monophonic lines are read off — the skyline, the bass, and a register-filtered melody; each is cut into four-interval n-grams (intervals, so transposition-invariant; no durations, so tempo- and rubato-invariant); each n-gram votes for a (theme, offset) pair in an inverted index. Three gates — ≥6 aligned hits, dense on their offset, clear of the best rival work — and below that it says nothing.

No model is called anywhere in the path, and a test greps for that. This matters for the brief: it is the part of the app that answers "what am I playing" without an LLM.

11.3 Where it runs

In a child process, started lazily, killed when idle. On an 8 GB machine, 497 MB is 6% of RAM for a feature that is on screen a few minutes a day. The IdentifyProxy actor:

  • spawns python -m fp30x_studio.identify watch --json when the identify panel opens or when a take is armed and "identify while I play" is on;
  • reads newline-delimited JSON verdicts off its stdout;
  • SIGTERMs it after 5 minutes with the panel closed and no armed take;
  • reports "corpus unavailable" honestly if themes.sqlite is missing — the loader already falls back to a 15-theme built-in stub with a loud banner, and the app must show that banner rather than present stub results as corpus results.

Cold start is 1.24 + 3.38 ≈ 4.6 s. The panel shows "loading corpus" for that, once.

11.4 Presenting a guess honestly

This is where the identifier is most likely to embarrass itself, and there are two documented ways it already has:

  1. Circular identification. Four segments of the session take identify as themselves at confidence 0.949 / 0.997 / 0.993 / 0.999, unchanged when the corpus doubled from 51,557 to 122,848 themes — which is what a tautology does. The labelling page already badges these by a substring test on Theme.source (JPA-151). The app must carry that badge. A verdict whose theme derives from a take in this collection is displayed as derived from your own take — not an identification.
  2. A confident label on a tiny window. Today the identifier returned Chopin, Polonaise-Fantaisie in A♭ Op. 61 at confidence 0.95 and 0.97 — on ~30-note windows out of 6,751 notes. That is a confident claim about 0.4% of the performance. Separately, on 2026-08-22 (cc8a92d) the Op. 62 No. 1 segment resolved to Anonymous, "HOERT DIE LERCHE SIE SINGT" Op. 150 with 6 aligned hits and margin 0.333 — a false positive, not silence, and the existing test test_removing_the_answer_from_the_corpus_produces_silence_not_a_guess does not catch it because it only generalises to a piece absent from the corpus.

So confidence alone is not a sufficient display. The verdict row shows four numbers, always:

🟣  Chopin — Polonaise-Fantaisie in A♭, Op. 61
    conf 0.95 · 6 aligned hits · margin 0.33 · covers 31 of 6751 notes (0.5%)

Coverage is the number that would have made today's guess self-evidently a guess, and it is not currently computed. Adding it is a small change in identifier.py and it is the single most valuable honesty feature in the identify path.

Two calibration figures worth encoding as UI thresholds:

  • The published retrieval result is ~11 notes for ~90% top-1 on a 968-work index, with the requirement growing logarithmically in corpus size — so on a 122,847-theme corpus the honest expectation is somewhere in the teens of notes, not six.
  • Every false-ish positive observed in this project has been 20–25 notes over 3–6 seconds — a Palestrina Sanctus on a warm-up, and the "HOERT DIE LERCHE" result above. That is a distinguishable regime. A verdict resting on fewer than ~30 notes is shown in a muted style with the note count first, not the work title first.

Against that: the good hits are unambiguous and worth keeping in the test set — segment 2 of 2026-08-20-a → Rachmaninoff, Prelude in D major, Op. 23 No. 4, conf 0.86, 6 aligned hits, density 1.0, margin 0.5; and Joplin, The Strenuous Life on 2026-08-17-piece.fp30 in 51 notes / 11.7 s, which JPA-148 records as the only independently measured identification figure in the project. The identifier also correctly returned no verdict at all on his C-major improvisation, which is mild evidence that it is not a piece.

Below the gates: nothing. Silence is the right answer when you are reading a terminal — or a window — out of the corner of one eye.
